# Стол для НРИ: контекст проекта для новых чатов

Этот файл нужен как стартовый контекст для будущих диалогов с Codex/ChatGPT. Если контекст чата потерялся, открой проект `new-chat` и приложи или процитируй этот файл.

## Коротко

Проект: браузерный онлайн-стол для НРИ / D&D battle table.

Текущий путь проекта:

```text
C:\Users\Misha\Documents\Codex\2026-05-16\new-chat
```

Стек:

- Vanilla HTML/CSS/JS, без сборщика.
- Node.js HTTP server без Express.
- Онлайн-синхронизация через REST + Server-Sent Events.
- Комнаты сохраняются в JSON-файлы в `.rooms`.
- Деплой использовался на Render.

Запуск локально:

```powershell
node server.js
```

Локальная комната:

```text
http://localhost:5173/?room=main
```

Render-комната:

```text
https://<render-service>.onrender.com/?room=main
```

## Главные файлы

- `index.html` — разметка приложения.
- `styles.css` — весь визуальный стиль.
- `app.js` — клиентская логика: состояние, canvas, инструменты, синхронизация, UI.
- `server.js` — HTTP server, комнаты, SSE, sanitization, merge/patch-синхронизация.
- `package.json` — минимальный npm script `start`.
- `.rooms/*.json` — сохранённые состояния комнат на сервере/локально. Не коммитить как исходник, это runtime-data.

## Render и трафик

Render Hobby workspace имеет лимит outbound bandwidth. В нашем случае Render показывал suspend после 5 GB free bandwidth.

Ключевая причина расхода была архитектурная: картинки раньше хранились как `data:image/...` внутри JSON state, и state мог многократно гоняться между клиентом и сервером.

Важно:

- Закрытая вкладка почти не тратит Render bandwidth.
- URL на музыку/картинку хранится как строка, сам mp3/ogg/image обычно грузится с внешнего сайта, а не через Render.
- Загруженные в приложение картинки как файлы превращаются в `data:image` и попадают в state, поэтому их обязательно сжимать.

## Уже сделанные оптимизации

### Сжатие изображений

В `app.js` есть `IMAGE_PRESETS`.

Текущие пресеты:

- `avatar`: max `256px`, quality `0.78`, WebP.
- `token`: max `720px`, quality `0.82`, WebP.
- `handout`: max `1400px`, quality `0.84`, WebP.
- `background`: max `2400px`, quality `0.86`, WebP.

Новые изображения сжимаются до попадания в state.

Старые `data:image` пытаются пережиматься при открытии комнаты через `optimizeCurrentImagesSoon()`.

### Thin image sync

Картинки не пересылаются повторно при обычных действиях.

Механика:

- Клиент считает `imagePayloadSignature`.
- Если набор картинок не изменился, outgoing sync отправляется без `src`.
- Сервер восстанавливает `src` из уже сохранённого room state.
- Broadcast тоже может отправлять state с `srcOmitted`, а клиент восстанавливает изображения из локального состояния через `hydrateRemoteImages`.

### Patch sync

Обычные действия могут отправлять `patch`, а не полный state.

На клиенте:

- `PATCH_FIELDS`.
- `serializeStateForSync()`.

На сервере:

- `MASTER_PATCH_FIELDS`.
- `SCENE_PATCH_FIELDS`.
- `applyMasterPatch()`.

Патч обновляет top-level state и активную сцену, чтобы переключение сцен не откатывало изменения.

### Cell delta для terrain/fog

Кисть/ластик и туман не отправляют весь объект `terrain`/`fog`, если это обычное рисование.

Клиент копит:

- `terrainSet`.
- `terrainDelete`.
- `fogSet`.
- `fogDelete`.

И отправляет:

- `terrainPatch`.
- `fogPatch`.

Полный `terrain`/`fog` всё ещё отправляется для крупных операций:

- закрыть весь туман;
- очистить туман;
- очистить краску;
- новая карта;
- прочие full-reset сценарии.

### Борьба с echo sync

Remote state больше не вызывает обратную отправку на сервер.

`applyRemoteState()` вызывает:

```js
renderAll({ shouldSave: false })
```

И сохраняет state локально без нового сетевого sync.

### Сетевой backpressure

Клиент не запускает параллельные POST `/state`.

Переменные:

- `syncPending`.
- `syncDirty`.

Если изменения пришли во время активного POST, следующий sync планируется после завершения текущего.

### Presence/cursor throttle

Presence был урезан:

- общий interval примерно `3000ms`;
- курсор не чаще примерно `700ms`;
- профиль отправляется только когда нужен (`includeProfile`), а не с каждым cursor update.

### Server gzip

`server.js` gzip-сжимает обычные HTTP/API ответы, если клиент поддерживает gzip.

SSE не gzip-буферизуется, чтобы не ломать поток событий.

### Отложенное сохранение `.rooms`

Сервер больше не пишет JSON-файл комнаты синхронно на каждый state update.

Вместо этого:

- `schedulePersistRoom(room, 1200)`;
- pending-комнаты сбрасываются на диск при `beforeExit` и `SIGTERM`.

Это уменьшает блокировки Node.js во время длинной игры.

### Server state hygiene

Сервер не должен слепо принимать бесконечно раздутый state даже от мастера.

В `server.js` добавлен `STATE_LIMITS` и `normalizeRoomState()`.

После full state, master patch и player merge сервер нормализует комнату:

- ограничивает число сцен, токенов, handouts, ассетов, шаблонов;
- режет `pings`;
- режет `rollLog`;
- ограничивает длину `playerNotes`, roll details и token notes;
- отбрасывает слишком большие `data:image`;
- ограничивает размер фоновых картинок отдельно от token/handout assets.

Это защитный слой от случайного раздувания комнаты, кривого клиента и слишком больших вставок.

### Принудительный sync

В панели комнаты есть кнопка мастера `Синк` (`forceSyncBtn`).

Она отправляет полный state с картинками:

```js
pushState({ forceFullImages: true })
```

Нужна как ручной режим восстановления, если сеть/Render/браузер глючили.

### Диагностика комнаты

В UI мастера автоматически создаётся блок `roomStats`.

Показывает:

- `State` — примерный размер JSON state.
- `Images` — вес картинок внутри state.
- `Tokens` — количество токенов / token assets.
- `Fog` — число клеток тумана.
- `Paint` — число клеток terrain.
- `Last sync` — размер последнего outgoing payload и время.
- `Patch` — какие поля ушли последним патчем.

Если значения становятся опасными, UI показывает warning:

- `state > 2 MB`;
- `images > 1.5 MB`;
- `sync > 200 KB`.

### Room compact / cleanup

В панели комнаты мастеру автоматически создаётся кнопка `Уплотнить`.

Она:

- удаляет неиспользуемые `tokenAssets`;
- удаляет неиспользуемые `handoutAssets`;
- чистит `pings`;
- подрезает `rollLog` до последних 12 записей;
- запускает пережатие старых изображений;
- делает `renderAll()` и sync.

Это полезно перед сессией или после удаления лишних токенов из библиотеки.

### Удаление токенов и ассетов

Токен с карты можно удалить:

- выбрать токен;
- нажать `Delete`;
- или нажать кнопку `Удалить с карты` в панели выбранной фигурки.

Картинку из библиотеки можно удалить крестиком `×` на asset card. Крестик увеличен стилями `.asset-delete`, чтобы его было проще нажимать вручную.

На сервере есть endpoint:

```text
/api/rooms/<room>/stats
```

Пример:

```text
https://<render-service>.onrender.com/api/rooms/main/stats
```

Возвращает JSON:

- `room`
- `revision`
- `clients`
- `stateBytes`
- `imageBytes`
- `tokens`
- `tokenAssets`
- `handoutAssets`
- `terrainCells`
- `fogCells`
- `scenes`
- `updatedAt`
- `persistPending`

## Важные технические детали

### State и scenes

Есть top-level state и массив `scenes`.

Активная сцена определяется `activeSceneId`.

Перед сохранением часто вызывается:

```js
saveActiveScene()
```

При применении сцены:

```js
applySceneToState()
```

При изменениях top-level поля активной сцены надо не забывать обновлять соответствующую сцену, иначе переключение сцен может откатить изменения.

### Player sanitization

Игрокам не должны уходить:

- hidden tokens;
- hidden handouts;
- hidden background;
- ассеты скрытых объектов.

Это делает сервер:

- `sanitizeStateForPlayer()`
- `sanitizeSceneForPlayer()`
- `collectVisibleAssetIds()`

### Player-created tokens

Игроки могут добавлять свои token assets.

Сервер ограничивает и чистит player-created token assets:

- `cleanPlayerToken()`
- `cleanPlayerTokenAsset()`
- `mergePlayerTokenList()`
- `mergePlayerState()`

Не ломать это при оптимизациях.

### Музыка

URL на музыку хранится как ссылка. Сам файл обычно не идёт через Render.

Локальный audio file создаёт `blob:` URL и является transient. Он не должен попадать в persisted state:

```js
musicTracks: (source.musicTracks || []).filter((track) => !track.transient)
```

## Известные риски

- Хранение картинок в JSON всё ещё архитектурно не идеально, даже после thin sync.
- Очень большая карта с текстом может пострадать от сжатия, если compression слишком агрессивна.
- SSE на Render может вести себя нестабильно при плохой сети, но текущие оптимизации должны снизить нагрузку.
- Если пользователь открыл старую комнату с огромными картинками, первый вход всё равно может быть тяжёлым, пока автооптимизация не пережмёт ассеты.
- `.rooms` на Render зависит от persistent disk/файловой системы сервиса. Если окружение эфемерное, комнаты могут теряться при redeploy/restart.
